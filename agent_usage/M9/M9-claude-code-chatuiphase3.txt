  1–2. Where CORS is configured / current allowed origins:
  backend/app/main.py:32-38:

      CORSMiddleware,
      allow_origins=settings.BACKEND_CORS_ORIGINS,

  settings.BACKEND_CORS_ORIGINS is defined in backend/app/core/config.py:21 as
  List[str], default ["http://localhost:3000"], overridable via the env var of
  the same name. Root .env.example:15 confirms:
  BACKEND_CORS_ORIGINS=["http://localhost:3000"]. docs/DEPLOYMENT.md never
  mentions BACKEND_CORS_ORIGINS in the Railway setup step — it's not in the
  documented deploy checklist at all.

  3. allow_credentials=True — yes, confirmed (line 35). This matters: it rules
  out ever using a wildcard * origin (disallowed by the CORS spec when
  credentials are enabled), so any fix must use an explicit list and/or a scoped
  regex, not a blanket allow-all.

  4. Is the failing origin allowed? No.
  https://rag-platform-kltizj8cj-iis-c-rag-platform.vercel.app is not in
  ["http://localhost:3000"], and there's no other entry — this is exactly the
  missing origin.

  5. Dynamic vs. hardcoded: Purely static — allow_origins is a fixed list from
  env. main.py passes no allow_origin_regex, so there is zero dynamic matching.
  That ...-kltizj8cj-... hash is a Vercel Preview deployment URL pattern
  (<project>-<hash>-<team>.vercel.app) — a new hash is minted on every preview
  build, so a static allowlist can never keep up with previews even if updated
  for today's URL.

  6. Why OPTIONS returns 400 before POST is ever sent: This is Starlette's
  CORSMiddleware.preflight_response(). On an OPTIONS request carrying
  Access-Control-Request-Method, it checks is_allowed_origin(origin); if the
  origin isn't in the allowlist, it appends "origin" to a failures list and
  short-circuits with PlainTextResponse("Disallowed CORS origin", 
  status_code=400) — the request never reaches the /auth/login route handler at
  all. (The preflight itself happens because the real request sets Content-Type:
  application/json, which isn't a CORS-simple content type, forcing the browser
  to preflight.)

  7. Recommended fix: Combine an explicit list with a scoped regex — not a
  blanket *.vercel.app regex, since allow_credentials=True means an overly broad
  pattern would let any Vercel-hosted app (not just this team's) make
  credentialed requests to this API.
  - Keep BACKEND_CORS_ORIGINS for the stable production origin(s) (e.g. the
  production Vercel alias and/or a future custom domain).
  - Add allow_origin_regex (Starlette's CORSMiddleware supports this natively
  but it isn't wired up in main.py at all today) scoped tightly to this
  project's preview naming, e.g.
  ^https://rag-platform-[a-zA-Z0-9]+-iis-c-rag-platform\.vercel\.app$, so every
  preview deploy is covered without per-deploy env edits.

  8. Code change, env change, or both: Both.
  - Code change (backend/app/main.py + a new field in
  backend/app/core/config.py, e.g. BACKEND_CORS_ORIGIN_REGEX) to actually pass
  allow_origin_regex=settings.BACKEND_CORS_ORIGIN_REGEX into CORSMiddleware —
  this parameter is currently never used.
  - Railway env change to set BACKEND_CORS_ORIGINS (stable prod origin) and the
  new regex var, since neither currently includes anything beyond the
  localhost:3000 default.
